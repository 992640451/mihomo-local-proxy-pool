# 指纹浏览器会话轮换设计草案

日期：2026-09-07。阶段：首期实现已完成，部署与验证结果见本任务记录。操作方式见 [会话轮换使用指南](BROWSER_SESSIONS.md)。

## 目标与建议

新增“会话轮换”策略：一次浏览器配置文件运行期间，所有经过该代理端口的流量固定使用同一个节点；下一次启动该配置文件时，按候选节点顺序选择不同节点。

示例：端口 17900 的节点顺序为 A、B、C。第一次启动使用 A，期间打开多个网站、刷新、创建连接均保持 A；退出后第二次启动使用 B，第三次使用 C，第四次回到 A。

推荐采用显式会话，由启动脚本或指纹浏览器自动化接口，在浏览器发出第一条代理请求之前创建会话。单纯在代理服务端观察流量，不能准确判断浏览器的启动和退出。

已确认一个浏览器配置文件独占一个端口。当前使用 Roxy Browser，但以后可能更换浏览器或使用普通浏览器。因此核心能力定义为通用的“端口使用会话”，浏览器种类只影响启动适配器，不写入节点轮换算法。尚未确认用户当前 Roxy 版本与账号是否已启用 API。

## 现有实现与问题来源

- `shared/portConfig.js` 的 `round-robin` 被映射为 Mihomo `load-balance` 策略组；界面已有描述“新连接依次分配给不同节点”。浏览器的一次运行包含很多连接，当前轮询粒度与需求不一致。
- `server/embeddedCore.mjs` 为每个端口生成独立的 `PPM-端口号` 策略组和 `ppm-端口号` listener，可复用这层隔离。
- `server/routes/ports.mjs` 已有端口配置、状态、检测接口，但没有浏览器运行会话的生命周期接口。
- `server/sessionStore.mjs` 保存的是管理后台登录会话，不能作为浏览器代理会话使用。
- `server/observability/service.mjs` 会定时通过端口发起出口检测；这类请求不能被算作浏览器启动。
- `server/index.mjs` 在应用启动时可能同步重载核心配置，因此节点绑定必须覆盖启动、热重载和订阅刷新路径。

Mihomo 的 `consistent-hashing` 按目标地址分配；`sticky-sessions` 按来源和目标地址分配，并有 10 分钟缓存期限，都不等同于浏览器运行会话。依据：[官方负载均衡文档](https://wiki.metacubex.one/config/proxy-groups/load-balance/)。

## 补全的产品规则

| 场景 | 默认行为 |
| --- | --- |
| 会话开始 | 按配置的节点顺序选择可用节点，绑定成功后才允许启动浏览器 |
| 同次运行中的多标签、跨网站、连接重建 | 始终使用同一节点，不按请求、目标域名、时间轮换 |
| 浏览器空闲、网络临时中断、电脑休眠 | 保留会话，不据此自动换节点 |
| 正常退出后再次打开，包括立即重开 | 结束旧会话，下一会话选择不同节点 |
| 同一启动操作重试 | 使用相同启动标识，返回原结果，不再次推进轮询 |
| 同端口已有另一个活动会话 | 返回冲突，要求结束旧会话；不能静默覆盖 |
| 会话内节点故障 | 固定原节点，连接失败并提示；节点恢复后继续使用原节点 |
| 下一节点故障 | 新会话开始前跳过；健康信息过期或未知时先进行有界检测 |
| 仅上次节点可用 | 默认拒绝开始新会话，提示“无其他可用节点”，不宣称轮换成功 |
| 所有节点不可用 | 新会话失败，不回退直连 |
| 应用/核心重启 | 恢复原会话绑定和轮询位置，不把服务重启当作浏览器重开；无法确认时进入待恢复状态 |
| 浏览器崩溃或启动器失联 | 不凭流量空闲换节点；优先由适配器核对配置文件运行状态，无法核对时提示人工结束 |
| 后台检查、代理预检、IP 检测 | 不创建、结束或推进会话 |
| 活跃会话下修改节点池、停用/删除端口 | 拒绝会破坏绑定的即时操作，提示先结束会话；无关配置可正常处理 |

这里保证的是“节点身份固定”。不同节点可能共享公网 IP，同一上游节点也可能动态更换出口 IP。若实际要求是公网 IP 在会话内恒定、下次必须不同，还需要静态出口资源、出口探测和按出口去重；不能只凭节点 ID 宣称满足。

“一次打开”定义为指定配置文件的一次独立运行，不是启动指纹浏览器管理软件、打开新标签页或刷新页面。只保证经过本端口的流量；未走代理的流量需要在浏览器代理配置中另外覆盖。

## 如何识别会话

| 方式 | 能力与限制 | 建议 |
| --- | --- | --- |
| 启动器/浏览器 API 明确开始与结束 | 可在首次请求前切换；同次运行空闲不变；立即重开可切换 | 正式方案 |
| 页面手动“开始新会话”，再自行打开浏览器 | 节点固定逻辑相同，但需要用户每次开始、结束，系统不会自动知道浏览器关闭 | 首期可用入口 |
| 端口零连接持续一段时间后推测结束 | 快速重开可能复用旧会话；浏览器未关但零连接可能误判；后台连接可能延迟结束 | 仅可作为后续独立的近似模式 |

不以源 IP 或源 TCP 端口作为浏览器身份。同机配置文件可能共享来源地址，而一个配置文件会创建许多源端口不同的连接。

如果必须同时满足“仅填写代理地址、不接入任何启动事件”和“每次打开精确轮换”，当前信息不足以实现可靠识别。缩短空闲超时不能消除这个限制。

### 通用入口与 Roxy 适配

页面提供“开始使用端口”和“结束使用端口”的通用入口，并为 Roxy 提供网页内的一键启动：用户在设置页连接 Roxy 本地 API，在端口编辑器中按团队、项目和窗口名称完成绑定；点击端口卡片上的“启动 Roxy”后，系统先创建端口会话、固定节点并同步代理，再打开对应窗口。窗口关闭后，系统通过 Roxy 运行状态自动结束会话。直接绕过该入口启动浏览器，不能承诺系统会识别为新会话。

Roxy 官方提供可启用的本地 API 和 API Key。当前适配使用工作空间、窗口列表、代理修改、打开窗口和连接状态接口；团队 ID、项目 ID 和窗口 ID 均由网页自动发现，仅在自动发现不可用时才展开手动 ID 兜底输入。依据：[Roxy API 说明](https://roxybrowser.cn/docs/api-documentation/api-reference.html)及[接口文档](https://roxybrowser.cn/docs/api-documentation/api-endpoint.html)。

更换浏览器只更换启动命令或适配器，端口、节点池、轮询状态和代理会话 API 保持一致。普通浏览器需使用独立配置目录，并核实启动命令是否复用已有进程；进程存在本身不能代替对应配置文件的运行状态。

Docker 中的管理服务通过 `host.docker.internal` 访问宿主机上的 Roxy 本地 API，便携模式直接使用 `127.0.0.1`。关闭窗口或崩溃由适配器查询对应窗口运行状态后结束会话；状态接口暂时不可用时保留绑定和当前会话，避免错误轮换。

## 推荐架构

数据路径继续由 Mihomo 转发：浏览器 → 固定端口 listener → 该端口的固定选择组 → 本次节点。管理服务负责开始/结束会话和选择节点，不在每条请求上重新做轮询。

应用新增策略标识 `session-round-robin`，在 Mihomo 中映射为 `select`。实现时将该组限定为本次绑定的一个实际节点；未使用时只有 `REJECT`。候选池保存在应用配置中，不能嵌套自动轮换组。应用保存策略语义，不能在读取 Mihomo 配置时把它反推成普通“手动选择”。

原设计考虑通过 `PUT /proxies/{group}` 选择节点。实现改为在会话边界写入单成员组并重载，再回读组状态核实；实际绑定同时写入磁盘配置，避免核心单独重启、热重载或选择缓存导致回到其他成员。真实 v1.19.28 核心已验证这一行为。官方 API 的连接列表及按 ID 关闭连接用于只清理该端口的遗留连接。依据：[Mihomo API 文档](https://wiki.metacubex.one/api/)。

控制器连接列表只用于诊断和连接清理，不能承担首个请求前的选点：观察到连接时，它可能已经走了旧节点。

### 开始会话

1. 启动器核实目标配置文件未运行，生成本次唯一 `launchId`。对已经运行的配置文件执行“打开/聚焦”不应创建新会话。
2. 请求开始会话；服务器检查权限、策略、节点池、配置版本和该端口是否已被占用。
3. 在端口级互斥保护下建立 `preparing` 记录；相同 `launchId` 重试复用记录，不产生第二次分配。
4. 从上次成功分配节点之后开始扫描有序候选池，最多一圈，排除上次节点并跳过不可用节点。首次使用从第一个候选开始。
5. 阻止边界期间的新流量，清理属于旧会话端口的残余连接。可以采用组内 `REJECT` 作为关闭状态；实际核心版本下的阻断、连接归属及 UDP 清理效果必须通过验证。
6. 持久化待选节点与 `activating` 状态，写入单成员策略组并调用 Controller 重载，回读核实，并持久化 `active` 与轮询位置后返回成功。
7. 启动器收到成功结果后，才调用浏览器 API 启动配置文件；启动失败应报告并结束本次会话。

API 超时不代表核心未切换，必须先查询同一 `launchId` 的结果再重试或补偿。数据库和核心不构成原子事务，异常留下可恢复的中间状态，不能凭 HTTP 状态简单重复换点。

轮询按“成功激活的会话”计数。若激活后浏览器启动失败，该分配仍计入轮询，避免因迟到请求、重试或短暂运行造成游标回退。

### 结束会话

启动器先关闭并确认目标配置文件退出，再提交携带准确 `sessionId` 的结束请求；服务器阻断此端口新流量，关闭该端口残留连接，完成后标记 `ended`。重复结束幂等；旧会话迟到的结束请求不得结束新的会话。

结束操作清理失败时保持 `ending` 或 `recovery-required`，阻止新会话开始。禁止调用关闭全部连接的 API 影响其他端口。

没有活动会话时端口处于未就绪/拒绝代理状态。浏览器的预检应在会话开始成功之后执行；后台对空闲端口的检查显示“未开始会话”，不能将其作为节点故障。

### 保存与恢复

新增独立的代理会话存储，建议复用现有 SQLite 迁移机制，记录端口、配置文件标识、`launchId`、`sessionId`、状态、选中节点 ID、上次分配节点 ID、候选池版本、开始/结束时间和待处理操作。持久化游标以稳定节点 ID 为基准，候选池有序，处理删除、重排和节点更名。

状态流转为 `idle → preparing → active → ending → idle`，任何结果不确定的操作进入 `recovery-required`。故障节点可以标记会话健康异常，但不能自动转成下一会话。

核心配置生成、订阅同步、端口更新、升级与重启恢复共用绑定逻辑：有活动会话时不得生成回到首节点或自动均衡的配置；无活动会话和无法恢复的中间状态应默认拒绝代理。必须验证核心选择缓存不会覆盖应用保存的绑定，禁止先开放错误节点再异步纠正。

刷新订阅时，活动会话引用的节点定义变化需要明确处理：首期建议拒绝激活会替换或移除该节点实际连接参数的变更，保留上一份可用配置，提示会话结束后重新刷新。添加无关节点可以正常更新，但热重载仍需保持原绑定。

恢复包可包含策略配置，但不恢复可直接复用的活动浏览器会话；恢复后从未开始状态进入。运行状态与原有登录会话分别管理。

## API 与界面

拟新增版本化接口，复用当前鉴权和审计，操作权限使用 `ports:write`，查询使用 `read`：

| 接口 | 作用 |
| --- | --- |
| `POST /api/v1/ports/:port/sessions` | 传入 `launchId` 和可选配置文件标识，创建或查询同次启动的会话结果 |
| `GET /api/v1/ports/:port/session` | 查询当前会话、节点和恢复状态 |
| `POST /api/v1/ports/:port/sessions/:sessionId/end` | 幂等结束指定会话 |

启动标识不是鉴权凭据。幂等记录必须跨应用重启保留；同一标识对应不同请求内容返回冲突。现有自动化 API 使用显式白名单，因此需要同步合同、schema、版本化路由及 CLI，不能只增加 UI 路由。

端口抽屉新增“会话轮换”，说明为“本次浏览器运行固定节点，下次启动切换”。保留原 `round-robin` 标识与行为，将显示名称明确为“按连接轮询”，避免破坏已有爬虫等用途。新建端口显式选择策略，已有配置不静默迁移。

界面显示当前节点、会话开始时间、会话状态、故障原因，并提供开始、结束及启动集成说明。下一节点可显示“预计”，实际分配仍要检查可用性。活动会话不提供无提示的“立即换节点”。

“验证代理池”在会话模式下改为验证本会话连通性和绑定稳定性，不切换节点，也不把多个节点共享 IP 当作轮换失效。完整轮换验证使用隔离测试端口，避免影响工作中的浏览器。

## 并发与部署范围

首期会话切换、端口修改和订阅激活复用内置核心全局变更队列，恢复操作另由 mutation gate 隔离。由于会话边界需要核心重载，串行化全部核心变更比单独端口锁更直接；可在后续优化并行健康检查。开始会话的候选检查有总时间上限，不能让订阅刷新覆盖刚完成的会话选择。

第一期优先支持受管内置 Mihomo 的 Docker 和便携部署。外部 Mihomo/Clash Verge 模式需在 Controller 能力、配置持久化和重载行为验证后开放；不满足条件时明确禁用新策略。

若多个配置文件要同时共用一个端口并各自拥有不同节点，端口级 `select` 无法满足，需要额外的身份认证与按会话分流入口。建议先为每个配置文件分配独立端口；该扩展不应混入首期。

## 实施顺序与验收

1. 核实浏览器启动 API/事件支持情况，验证现有固定版本核心的选点、缓存、重载、默认拒绝和按端口连接清理行为。这一步决定首期启动适配器和异常恢复的可实现边界。
2. 完成策略配置、代理会话存储、选点状态机、Controller 操作、互斥和恢复；覆盖两种部署的受支持路径。
3. 增加版本化接口、CLI、界面以及检测隔离；接入启动器，确保没有“浏览器先发请求、再换节点”的窗口。
4. 增加单元测试与真实核心集成测试，再进行目标指纹浏览器端到端验收。

核心验收场景：

- A/B/C 三个可控节点连续启动得到 A、B、C、A；同次运行对多个域名建立大量并发 HTTP、HTTPS CONNECT、SOCKS5 连接，全部绑定相同节点。
- 关闭后立即重开轮换；空闲超过 30 分钟、连接数暂为零、断网和休眠恢复不轮换。
- 重复开始请求只分配一次；两个不同启动请求竞争同端口时只有一个成功；旧结束请求不干扰新会话。
- 会话内节点失败不切换、不直连；下一会话跳过故障节点；无其他可用节点时明确失败。
- 应用重启、核心重启、订阅刷新、无关端口编辑保持已有绑定；核心/数据库操作中途失败可恢复且不错误报告成功。
- 自动检测、端口预检和验证按钮不消耗轮询；未开始的端口不被检测任务激活。
- 切换前清理旧连接，其他端口长连接保持；已支持的 UDP 转发也须固定节点并验证会话结束清理。
- 浏览器启动失败、崩溃、退出通知丢失及 API 超时均能查询实际状态并继续处理。

节点身份应通过可控上游或核心实际连接链验证；公网 IP 仅作辅助，不能替代节点身份判定。

实施阶段按仓库要求执行测试、构建、Compose 配置检查，并在交付前运行 `npm run docker:update` 验证容器健康。Roxy 适配器使用官方接口完成并通过模拟生命周期测试；未取得用户安装实例的 API 配置，不能将其描述为已完成真实 Roxy 端到端验收。普通命令适配器要求独立进程，快速重开需等待上一启动命令输出 ended。
