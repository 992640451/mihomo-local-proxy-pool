# 已部署设备升级方案（设计稿）

日期：2026-09-03。本文保留升级能力的设计基线与后续规划；当前实现的入口、部署要求和发布签名配置以 [网页版本更新](UPDATING.md) 为准。根据用户补充要求，参考 sub2api，将页面内提示、主动更新、自动重启和重连纳入第一期。

## 1. 建议与范围

采用“页面 Tip 提示新版 → 用户确认更新并自动重启 → 后台下载校验 → 重启提示 → 完整备份 → 切换版本并启动 → 验证 → 页面重连”的流程，失败时按阶段继续运行旧版或恢复快照。支持 Windows/Linux/macOS 便携包，以及已接入更新代理的 Docker Compose 部署。

管理员登录后异步检查一次版本，服务端缓存建议 6 小时；页面持续打开时每 6 小时刷新一次，可手动检查，也可关闭自动检查。关闭后只使用本地版本与手动检查结果，不主动访问发布源。检查不会安装更新，检查失败不影响代理服务。默认仅提示正式版，测试版由用户主动选择。首期接受短暂维护停机，不承诺代理连接不中断。

普通用户不应重新初始化、重新配置订阅或手工合并文件。程序版本与持久数据分开管理，管理员账号、加密密钥、订阅、端口池及设置在成功升级后继续使用。

## 2. 当前基础与缺口

以下结论来自当前工作区，不能据此认定远端已经发布相同产物。

| 当前基础 | 升级设计需要补齐的部分 |
| --- | --- |
| `package.json` 为 1.2.0；系统设置已有版本、构建提交及 Node/Mihomo 信息 | 明确部署方式、更新能力和最新可用版本 |
| 发布流程已有六平台便携包、GHCR 镜像、校验和及构建证明 | 机器可读的更新清单、兼容范围、更新执行器 |
| `scripts/docker-update.mjs` 构建并重建管理容器，等待健康检查 | 宿主机完整备份、固定目标版本、核心联动升级、失败回退 |
| 便携启动器支持启动、停止及 `PPM_DATA_DIR` 等路径配置 | 独立更新进程、程序版本切换、首次接入升级流程 |
| SQLite 已有顺序迁移、事务及迁移前单库备份 | 多数据库、配置、密钥和核心状态的同一恢复点 |
| `/healthz` 返回管理进程存活信息 | 验证实际版本、数据库可读、核心就绪和端口恢复 |

现有加密配置恢复包不含管理认证、会话、API 令牌、审计、检测历史与检测调度设置，不能代替升级快照。数据库代码会拒绝由更高结构版本创建的数据库，不能假设换回旧程序就能回退。

便携版目前将 `core/config.yaml` 放在程序目录的 `core` 下；升级时必须识别并保留。Docker 既有默认 Compose，也有 `compose.aliyun.yaml`、legacy override 等变体，不能一律套用新部署模板。

## 3. 用户如何更新

全局导航保留版本标记，有更新时显示提示点；首次发现兼容的新版本时，在页面右上角弹出非阻塞 Tip：“发现新版本 vX.Y.Z”，提供“查看更新”和“稍后”操作。同一管理员、同一安装、同一目标版本在同一天最多主动提示一次；“忽略此版本”只隐藏主动提醒，设置页仍可更新。未登录不提示。仅比较大小且兼容性通过的版本可显示可升级提示。

在“系统设置”增加“版本更新”卡片，显示当前版本、最新兼容版本、发布时间、更新说明、部署方式和上次检查时间。检测失败显示“暂时无法检查”，不能显示“已是最新版”。

| 部署方式 | 首期用户操作 | 更新执行位置 |
| --- | --- | --- |
| Windows 便携包 | 点击“查看更新”→“更新并自动重启”→等待页面恢复 | 包内独立更新进程 |
| Linux/macOS 便携包 | 与 Windows 相同，在页面完成 | 包内独立更新进程 |
| Docker 发布镜像（已接入代理） | 与便携版相同，在页面完成 | 独立 updater 服务管理本项目 Compose |
| 未接入代理的 Docker / 自定义源码安装 | 页面提示新版及一次性接入步骤；源码定制仍提供固定版本的手动指引 | 宿主机接入程序或原有运维流程 |

以上入口尚未实现。页面根据后端返回的更新能力展示操作，未接入执行器时显示“启用网页更新”或“查看更新方法”，不能提供一个实际无法完成的更新按钮。新的标准部署默认附带所需执行器。管理容器继续使用现有最小权限部署，Docker socket 只交给独立 updater。

更新确认弹窗展示当前/目标版本、更新说明、将保留的数据、备份位置、是否同时升级 Mihomo及停机影响。主按钮明确为“更新并自动重启”，一次确认授权本次安装与服务重启；不要求下载后再确认一次。

页面按以下状态显示，版本号均为示例，不代表已发布：

| 状态 | 页面文案与行为 |
| --- | --- |
| 发现版本 | “发现新版本 vX.Y.Z”，查看更新或稍后 |
| 下载与校验 | 展示实际下载进度；校验等无可测百分比的阶段只显示阶段名 |
| 准备完成 | “新版本已准备就绪，5 秒后将开始备份并重启服务”，由后台记录倒计时终点 |
| 备份与切换 | “正在备份并安装，请稍候”；失败显示具体阶段 |
| 自动重启 | “正在启动新版本，页面将在服务恢复后自动连接” |
| 验证成功 | “已更新至 vX.Y.Z，服务已自动重启”，刷新页面资源 |
| 自动回退成功 | “本次更新失败，已恢复至 vA.B.C”，显示原因及日志入口 |
| 仍未恢复 | “暂时无法连接服务”，保留检查状态及本机恢复指引，不猜测成功或失败 |

取消仅限下载/校验/倒计时阶段且由执行器确认；快照与切换开始后不再中断事务。浏览器关闭、刷新或切换页面不取消已授权的后台任务。这里自动重启的是服务，不是用户设备。

### 页面与后台协作

新增统一更新任务 API（路径为设计建议）：

- `GET /api/system/updates`：当前版本、最新兼容版本、更新说明、检查状态，以及 `canUpdate`、`canAutoRestart`、`unsupportedReason`。
- `POST /api/system/updates/check`：显式重新检查，服务端限频并合并并发请求。
- `POST /api/system/updates/jobs`：提交已确认的目标版本、清单摘要、自动重启选项和幂等键；执行器持久接收后返回 `202` 与 `jobId`，不等待整个下载完成。
- `GET /api/system/updates/jobs/:jobId`：阶段、实际进度、目标版本、重启时间、失败/回退结果。所有状态由执行器持久保存，Web 服务只转发。
- `POST /api/system/updates/jobs/:jobId/cancel`：仅准备阶段允许取消，已开始切换时返回明确的状态冲突。

执行器再次校验目标与清单，不因下载期间发布了更新版本而静默改变本次目标。同一安装同时只运行一个更新任务；重复请求返回已有任务，不重复安装。

浏览器只保存非敏感的安装标识、任务 ID 和目标版本；正常时轮询任务，重启期间采用有退避的状态重试。页面无法访问时保留原页面与已知阶段，不持续强制刷新。连接恢复后查询同一任务的最终结果，确认实际运行版本/提交与目标一致、业务检查通过，再显示成功并只自动刷新一次。不能把 `/healthz` 的 200 或“重启请求已受理”当作升级成功。

维护状态下仍允许经过认证的任务状态读取和执行器健康验证；业务写入保持关闭。管理进程存活检查与最终业务就绪检查分开，避免 Compose 等待管理服务健康、管理服务又等待尚未启动的核心造成互相等待。

若会话失效，转登录并在重新认证后继续查询原任务；新旧任务查询协议需跨版本兼容。UI 等待超过建议的 180 秒后显示恢复指引并允许继续检查，超时本身不触发第二次更新或推断回退。发布资源使用内容哈希，入口 HTML 与版本/任务接口不缓存，避免重启后继续展示旧页面。关闭浏览器的用户下次登录时也能看到尚未确认的最终结果。

## 4. 老版本如何首次接入

没有更新入口的版本，通过 Release 下载支持迁移的新包或宿主机脚本完成第一次升级并安装执行器；旧页面无需先具备新功能。这是一次性接入，之后可在页面完成更新。不能让完全没有更新能力的旧版本凭空获得该按钮。

便携版更新器从新包运行，读取旧安装的构建信息与真实数据路径，识别是否在运行、能否使用原启动器正常停止。未知版本、路径冲突或无法确认进程归属时，只做预检并提示人工处理，不按端口直接终止进程。发现旧数据但缺少密钥时阻止升级，不能自动生成新账号或新加密密钥。

首次迁移将旧目录转换为稳定安装根目录：根目录保留启动入口，程序进入 `releases/<版本>/`，当前版本记录在指针文件；默认 `data/` 保持原路径。自定义外置数据路径继续保留。核心运行配置迁入数据目录，核心二进制随版本保存在发布目录。逐步写入迁移日志，旧程序与原配置在验证成功前保留。

修改业务数据前，先保存原启动入口并安装持久启动保护，检查原脚本、快捷方式指向及已注册的自启动项，确保正常启动路径会先检查未完成的事务。发现无法接管的旧服务或自启动项时停止自动迁移，提示先处理该项。用户不得绕过启动器直接运行旧程序访问同一数据；仅保留旧目录不能视为已隔离旧实例。

Docker 首次接入读取实际 Compose 项目名、文件组合、环境配置、卷名、bind mount、镜像及端口映射，写入本机部署记录，并添加独立 updater 服务与配对凭据。继续使用原项目与卷；无法可靠识别时先展示缺失项，不能默默创建新卷或覆盖原 `.env`。

## 5. 发布端与版本发现

在现有 Release 流程增加 `update-manifest.json`，至少包括：清单格式版本、应用版本、源码提交、发布通道、支持的来源版本、更新器最低版本、各数据结构迁移范围、平台与架构、包大小和 SHA-256、镜像 digest、配套 Mihomo 版本及 digest、部署模板版本、是否需要重启核心、发行说明链接。

新版本在制品齐备、校验完成且 Release 公开后才可被客户端发现。客户端仅使用固定项目的公开发布源，忽略 draft，按语义化版本和升级兼容范围选择目标；未知清单格式、不支持的系统/架构、未知数据库结构均禁止直接升级。跨版本不兼容时列出中间版本，不直接跳过。

清单与制品建立签名信任链：客户端内置验证公钥，发布流程使用独立签名凭据签署清单；清单绑定包摘要和镜像 digest。支持有验证依据的公钥轮换，不能只依赖同站下载的哈希文件证明来源。继续保留现有 provenance。发布流水线只有生成并验证签名后才公布更新清单。

在线下载在停机前完成；网络受限时允许用户下载完整离线更新材料，包括包/镜像归档、签名清单和匹配的核心。校验、适配和磁盘空间检查在本机执行，无需上传订阅或设备配置。

## 6. 更新执行与恢复

统一步骤如下，两个部署执行器共享规则，但各自管理程序生命周期。

1. 获取单实例更新锁，确认来源版本、目标身份、支持范围、真实数据路径、文件权限和磁盘空间；清点程序、多个数据库、核心状态与外置配置。预留新包解压、完整快照及失败现场空间。
2. 下载/导入并验证全部产物，在隔离暂存目录完成解压或镜像拉取。拒绝越界归档路径和指向目标外的链接；断网或校验失败时旧服务继续运行。预先保留旧程序/旧镜像，回退不依赖联网。完成预检后，执行器写入准备就绪状态与 5 秒倒计时终点，按已授权的自动重启选项继续，浏览器计时器不控制实际执行。
3. 写入持久更新事务记录并进入维护状态，阻止新写入，停止调度，等待正在进行的写入结束。首期正常停止管理服务与内置核心，确保数据库连接关闭；确认所有相关写入者已停止后才复制文件。
4. 生成完整升级快照并核验可读性、清单和校验和；保留必要的 SQLite WAL 文件及其关联，不能只复制正在写入的主库。快照未完成不得开始切换。
5. 切换程序、执行必要的数据/配置迁移，启动目标版本。维护状态必须贯穿目标启动过程，目标在放行前不接受业务写入，不运行后台调度。
6. 验证实际应用版本/提交、数据库完整性与订阅解密、端口池配置、Mihomo 控制器及预期监听端口。无端口配置时跳过监听检测。公网出口检测作为可选诊断，网络不通本身不触发版本回退。
7. 验证通过后提交事务并解除维护状态，记录升级结果和可用备份；前端重新连接或要求重新登录。保留至少最近一次成功升级前的恢复点，清理由后续保留策略管理，不能在升级中删除唯一恢复点。
8. 按失败时是否已经改变程序或数据进行恢复：停服前失败则旧服务继续运行；已停服但尚未切换、快照失败时，撤销维护设置并重新启动原服务，不使用不完整快照。切换、迁移、启动或验证任一步骤失败且尚未开放业务写入时，则停止相关服务，保留失败现场，将旧程序/镜像、配置、密钥和全部相关数据恢复到同一有效快照。恢复按快照清单重建精确文件集合，不能仅覆盖同名文件；失败版本新增的数据库、WAL 和配置一并隔离。进程 PID、服务锁和控制令牌等临时运行状态由启动器重建，不作为有效运行实例恢复。完整核验所有恢复目标后才启动并验证旧版本。恢复步骤可重复执行，恢复失败时进入“需要人工恢复”，报告恢复点和日志，不能显示“回退成功”。

事务记录与更新日志放在独立控制目录，不能随着业务数据回滚被覆盖。记录准备、快照完成、已切换、验证中、已提交、回退中及最终结果。关键记录持久落盘后再推进下一步。停机前将自包含的恢复执行器、所需运行时和操作入口放到稳定控制目录，不能只依赖可能被移动或删除的新包目录。

正常更新期间独立执行器持续运行，负责自动启动目标服务；服务重启与整机断电恢复是两个场景。便携版断电后由用户重新运行启动/恢复入口，先根据事务恢复再启动业务，不新增开机自启承诺。Docker updater 独立设置重启策略，在 Docker 恢复后继续未完成事务；若 updater 自身无法启动，保留宿主机恢复命令。未完成事务时，正常业务启动入口应阻止直接启动混合状态。Docker 应在停机前记录并临时约束业务容器自动重启，重建目标容器时也保持该约束，事务完成后还原原策略。

自动回退覆盖本次升级从开始切换到验证完成、尚未开放业务写入的整个阶段。已成功升级并使用一段时间后的降级，需要用户明确接受恢复到旧快照会丢失之后的变更；没有验证过的数据向下兼容性时不能只换旧二进制。

## 7. 两种执行器的重点

### 便携包

稳定启动入口读取当前版本指针，以明确的程序根目录和数据根目录启动。每个发布目录包含配套应用、Node 与 Mihomo。启动时准备独立更新器与受限的本机控制通道，更新任务在脱离 Web 服务生命周期的进程中执行；该进程不在应用退出的清理逻辑中被终止。Windows 后台进程隐藏窗口，不要求用户手动重开启动器。

更新器从稳定控制目录或独立暂存位置运行，保留自用 Node；确认旧进程退出后切换并启动新程序，避免覆盖自身正在使用的运行时，兼容 Windows 文件占用限制。更新器本身的升级采用下一次任务启用的独立版本，首期业务更新不能中途替换当前执行器。

首期完整停机更新，快捷方式继续指向稳定安装根目录。迁移前已有外置 `PPM_DATA_DIR`、`PPM_CONFIG_FILE`、`PPM_CORE_DIR` 或自定义核心的安装必须完整盘点；首期无法验证的自定义核心组合只提供手工升级指引。

### Docker

面向正式部署提供专用发布 Compose 模板，应用和核心镜像固定到 digest。既有用户更新时继承实际项目名、卷与覆盖配置；新模板只能经过映射预检后采用。不要硬编码假设所有用户的卷都叫同一个名称。

新增独立 `updater` 服务，包含受控更新程序和 Docker/Compose 工具，持久保存部署注册信息、任务与恢复点。updater 不依赖管理服务的健康状态，也不被本次业务容器升级重建；自己的更新走单独兼容流程。

Docker socket 仅挂载给 updater，它具备较高宿主控制权限；API 必须限于已登记的本项目、允许的卷/路径和签名发布目标，拒绝任意命令、容器 ID、镜像或文件路径。其控制 API 不发布宿主端口，只在专用内部网络供管理服务访问，使用安装时生成的配对凭据认证并防止重放。管理员请求在管理服务验证后，再转交 updater 独立校验。

updater 以注册的有效部署配置重建容器，通过受控工具读取/恢复已登记数据卷；不能简单把宿主部署目录复制进 updater 后套用相对路径。Compose 渲染得到的 bind mount 来源必须保持真实宿主绝对路径并经过预检。任务控制目录与配对凭据独立于会被回滚的业务数据。

完整备份包含 `.env`、有效部署配置、`proxy-session-data` 与 `proxy-mihomo-data` 对应的实际卷，以及所有相关可写 bind mount（例如历史 catalog）。备份存放在更新操作之外的宿主机目录，保留权限、所有权并限制读取，因为它含密钥。

以 `pull/load → stop → 快照 → 应用目标配置 → up → 业务验证` 为顺序。Compose `--wait` 是进程/容器健康检查门槛，后面仍需上述业务验证。首期备份时停止两个服务；核心升级时使用清单指定的配套镜像，不能仅依赖目前带 `--no-deps` 的开发更新命令。

源码部署固定正式标签/提交后构建，不将分支最新提交当作正式版本。若用户有本地修改，在独立目录准备目标，原部署配置与修改保留；不能自动 reset、stash 或切换用户工作区。

## 8. 实施顺序与验收

建议第一期交付页面更新完整闭环，内部依次实现发布清单、独立执行器、更新任务 API、Tip 与重连界面。只完成 Tip 不算完成第一期。

| 阶段 | 交付内容 | 用户获得的能力 |
| --- | --- | --- |
| 第一期 | 签名清单；新版 Tip；更新确认与持久任务；便携执行器；Docker updater 与旧版本一次性接入；完整快照、维护模式、迁移与回退；自动重启、重连及版本核验 | 标准便携和已接入 Docker 部署均可在页面点击更新，完成后自动重启并提示结果 |
| 第二期 | 页面导入离线更新材料、预约更新时间、更多部署变体适配、可配置备份保留策略 | 扩展网络受限场景和更新偏好 |

第一期即校验管理员身份、同源/CSRF 防护及安装归属；只接受已验证发布清单中的版本，不能接受任意下载地址、路径或命令。更新任务与取消操作记录脱敏审计；普通业务 API 令牌不能调用更新能力。正常 Web 服务退出后，更新代理仍可完成操作并提供结果。

验收覆盖每条声明支持的来源版本升级到目标版本，不能只验证全新安装。至少使用脱敏夹具包含订阅、端口池、会话、令牌、审计和检测设置，检查成功升级后的保留，以及失败回退后的成套一致性。

必须覆盖：下载中断、摘要/签名错误、空间不足、备份失败、迁移失败、核心启动失败、端口冲突、切换时断电、回退失败；Windows 中文/空格路径与文件占用；两种 CPU 架构；Docker 项目名、外置数据、legacy 与部署覆盖配置。验证阶段要确认后台写入确实被阻断。

页面闭环还需覆盖：同版本提醒去重、忽略版本、多个标签页同时点击更新、长下载与反向代理超时、关闭页面后继续执行、倒计时由服务端推进、重启导致的连接中断、会话失效后恢复任务、旧版本仍返回 200 但不能报成功、资源刷新后版本一致、未安装执行器时正确显示接入指引。网络请求返回 401/403 或明确拒绝时不能统一当作“正在重启”。

## 9. 实现依据

项目依据：`scripts/launcher.mjs`、`server/runtime/paths.mjs`、`scripts/docker-update.mjs`、`server/database/migrations.mjs`、`server/routes/system.mjs`、`server/recovery/service.mjs`、`compose*.yaml`、`PORTABLE_ZH.md`、`DOCKER_ZH.md` 和 `RELEASING.md`。

Docker 重建可保留挂载卷，但这不等于升级备份；参见 [Compose up](https://docs.docker.com/reference/cli/docker/compose/up/)。默认项目名受目录影响，迁移需继承原项目身份；参见 [Compose 项目名](https://docs.docker.com/compose/how-tos/project-name/)。SQLite 在线一致性备份应使用其备份机制；首期采用正常停机后的完整快照，后续若减少停机时间，再设计跨库协调，参见 [SQLite Backup API](https://sqlite.org/backup.html)。
